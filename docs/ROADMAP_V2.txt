===============================================================================
WHY THIS DOC EXISTS
===============================================================================
Today we found the v1 correction engine (wav2vec2 forced-alignment, grades
Madd/Ghunnah DURATION only) will happily grade English or French speech as if
it were correct Qur'an recitation — because forced alignment never checks
WHAT was said, only stretches the known-correct text over whatever audio it's
given and measures timing. That's a trust-breaking gap for a "coach" app.

The user's ask, reorganized into a buildable sequence:
  1. Verify the person actually said the right letters/words (not just timing).
  2. Per-word red/yellow/green feedback, shown after they finish an ayah/surah.
  3. A "why" explanation per mistake (which tajweed rule, what went wrong).
  4. A Duolingo-style drills screen to practice individual tajweed rules,
     available any time, with instant correction + encouragement.
  5. A memorization (hifz) tracker per surah/ayah.
  6. Spaced repetition (SRS) scheduling built on top of the tracker.

Guiding constraints (explicitly requested): FAST, TRUSTED, LOW-RESOURCE.
  - Fast: CPU-only, local, no GPU dependency, no multi-second dead air.
  - Trusted: don't grade "correct" when the content is wrong; show confidence,
    not false precision. Keep a regression set of known-good/known-bad
    recordings so every new feature is checked against real evidence, the way
    Phase 4's sensitivity test (scratchpad/validate_wrong.py) proved the
    duration gates actually catch injected errors, not just avoid false
    alarms.
  - Low-resource: reuse the ALREADY-LOADED wav2vec2 model for new checks
    instead of adding new heavy models, unless a cheap option is proven
    insufficient first.

===============================================================================
PHASE 0 — Content-sanity check (small, do first, unlocks everything else)
===============================================================================
Goal: stop grading recitations that don't match the expected text at all.

What: the wav2vec2 model already produces frame-level letter probabilities to
do forced_align (server/app.py -> tajweed.correction.aligner). Add a plain CTC
GREEDY DECODE pass over those same logits (near-zero extra cost — same forward
pass, just a different readout) to get a rough Arabic transcript of what was
actually said. Compare it to the expected ayah text via normalized edit
distance (reuse `normalize_arabic` from metadata.py — already strips harakat
so this is a consonant-skeleton comparison, forgiving of the model's known
diacritic weaknesses).

Decision rule (tune empirically against real recordings, both correct and
wrong-language/wrong-ayah):
  - CER low -> proceed to tajweed grading as today.
  - CER high -> return a new status "content_mismatch" instead of a graded
    report ("This doesn't sound like this āyah — check you selected the
    right one, or try again closer to the mic").

Why this order: it's the cheapest possible fix (no new model, no new infra),
and it directly closes today's trust gap. Everything below (word-level
grading, drills, SRS) inherits this check for free once it's built once.

PHASE 1 — Word-level scoring engine (green/yellow/red)
===============================================================================
Goal: move grading granularity from "per tajweed-rule segment" (today) to
"per WORD", combining two independent signals per word:
  (a) Content correctness — was this word recognized at all (from Phase 0's
      decode), aligned word-by-word (Levenshtein/DTW over the word sequence,
      not just a whole-ayah CER).
  (b) Tajweed correctness — for any rule segments touching that word, reuse
      the existing measure_segment/rules.py machinery (already built,
      calibrated, one-sided where appropriate).

Combine into one verdict per word:
  - RED    = word missing/misrecognized (content problem — most important,
             a tajweed timing check on a wrong word is meaningless).
  - YELLOW = word correct, but a tajweed rule on it measured "warn".
  - GREEN  = word correct AND all tajweed rules on it "ok" (or no rule
             applies).

This is the architectural core of "an architecture that analyzes just that
surah and shows where the tajweed mistakes are" — it's the same evaluate()
pipeline we have, restructured to key its output by word_idx instead of by
rule, with content-correctness folded in as a first-class signal instead of
assumed.

Frontend: extend GradedAyah (app/src/screens/Practice.tsx) from
rule-coloring to word-coloring; each word gets a tap/hover explanation
("idghaam held 4.2 h, expected 2 — a bit long" or "expected 'الرحمن', not
recognized"). This is an incremental change to an existing component, not a
rewrite.

TWO REAL BUGS FOUND + FIXED while validating against real reciter audio
(same discipline as Phase 0 — test on real data, not just synthetic):
  1. **Basmala prefix (real, pre-existing gotcha, same one Phase 4's
     audio_verify.py already handles for DURATION).** quran-uthmani.txt
     prefixes the basmala to the TEXT of ayah 1 of every surah except 1
     (where the basmala IS the ayah) and 9 (no basmala) — but reciter AUDIO
     of ayah 1 usually omits it. Before the fix, this made the 4 basmala
     words show "red" (wrong) on an otherwise-PERFECT 112:1 recitation.
     Fixed: `_strip_basmala_prefix()` in word_score.py excludes those 4
     words from scoring entirely (mirrors audio_verify.BASMALA_NORM's
     letter-count stripping, duplicated locally rather than imported to
     avoid pulling audio_verify's mutagen dependency into the correction
     package). Verified on real 112:1 audio: all 4 real words now green.
  2. **CONFIRMED the Phase-0 short-ayah gap is real AND that Phase 1 fixes
     it**, exactly as hoped in Phase 0's Open Decisions note: fed 1:1 audio
     (Basmala) against 112:1's expected text — Phase 0's whole-text CER
     (0.43) stayed under the 0.75 threshold ("ok", missed it), but Phase 1's
     word-level scoring correctly marks ALL 4 words "red" (none of 112:1's
     words appear in the Basmala's decode). This is real, validated evidence
     that word-level granularity is a genuine improvement, not just a nicer
     UI — keep this as the reference case if the approach is ever revisited.

KNOWN REMAINING LIMITATION (documented, not fixed — low risk to "fix"):
  the LAST word of an ayah can show a false "red" because the raw (non-Quran-
  tuned) CTC greedy decode sometimes truncates a long held madd at the very
  end of the utterance (observed: 1:1 real audio decoded "...الرَّحِ" instead
  of "...الرَّحِيمِ", even though content_status was "ok" overall, cer=0.11).
  Considered a "fuzzy prefix match" fix (treat a hyp word as matching a ref
  word if it's a real prefix covering most of its length) and REJECTED it:
  Quranic Arabic has many real minimal-pair-style words sharing long prefixes
  but differing in ENDING (e.g. الرحمن vs الرحيم both start "الرح") — exactly
  the kind of word-ending mistake that matters most for tajweed. A fuzzy
  prefix match would systematically HIDE real ending mistakes to paper over
  an ASR truncation artifact — worse trade than an occasional false red on
  the ayah's last word. Leave exact matching; revisit only with a smarter
  signal (e.g. per-frame decode confidence) if this becomes a UX complaint.

PHASE 2 — Whole-surah flow (record once, grade at the end)

concatenates), get ONE combined report when they stop, with the entire surah
text rendered and word-colored (extends Phase 1's per-word coloring across
every ayah, not just one).

Two sub-approaches, pick based on how Phase 0/1 perform in practice:
  A) Batch-after-stop: user records the whole surah, app slices audio by
     ayah boundaries (silence-gap detection or just accepts one file per
     ayah recorded in sequence) and calls /grade per ayah, aggregating. Uses
     server/batch.py's aggregation logic, which ALREADY exists and is tested
     — mostly a frontend orchestration + UI job, not new ML.
  B) Streaming-per-ayah: grade each ayah as soon as the user finishes it
     (e.g. on a pause/tap "next ayah"), so feedback appears progressively
     instead of one big wait at the end — better "fast" feel for long surahs.
     Recommended over (A) for surahs beyond a few ayahs.

**SUPERSEDED same day by continuous single-take recitation (2026-07-06):**
the button-per-āyah flow above was immediately replaced — user asked to
recite the WHOLE page in one continuous take with no button-pressing, the

only on a mistake, letting the reciter re-do just that āyah and carry on.
Built:
  - `app/src/lib/pauseDetector.ts` — pure, framework-free state machine
    (`stepPauseDetector`) deciding from a stream of RMS samples when a
    silence gap counts as an āyah boundary: never cuts before any speech in
    the segment (ignores a leading breath), never cuts shorter than
    `minSegmentMs`=1200ms even if paused (guards a stray cough), cuts once
    `pauseMs`=700ms of continuous silence follows real speech. Verified with
    a standalone node script (no JS test framework in this repo) against 4
    synthetic RMS traces: leading-silence-only (no cut), real pause (cuts at
    the right time), short breath (no cut), pause-but-segment-too-short (no
    cut) — all behave as designed. Defaults (`speechRms`=0.02, `pauseMs`=700,
    `minSegmentMs`=1200) are REASONABLE STARTING POINTS, NOT validated
    against real microphone/recitation audio (no way to record real speech
    in this automated environment) — expect to retune against real usage,
    especially `pauseMs` (waqf pauses vary a lot by reciting style/speed).
  - `app/src/hooks/useAutoRecorder.ts` — ONE `getUserMedia` stream for the
    whole session (mic permission granted once). Key trick avoiding manual
    PCM slicing: MediaRecorder's chunked webm/opus output can't be sliced at
    an arbitrary timestamp (only the FIRST chunk carries the container
    header, so a later subset alone won't decode) — so each detected
    boundary instead STOPS the current MediaRecorder (yielding one complete,
    independently-valid blob via the existing `blobToWav16kMono` pipeline,
    unchanged) and IMMEDIATELY starts a new one on the SAME stream. No gap
    the user would notice, no second permission prompt. An AnalyserNode +
    requestAnimationFrame loop feeds live RMS into the pause detector and
    also drives a UI volume meter. `onSegment` callback is stored in a ref
    reassigned on EVERY render (not inside an effect) so the async
    `MediaRecorder.onstop` handler — which can fire well after the render
    that queued it — always calls the current callback closure; this is
    what lets Practice.tsx's `handleSegment` reference the live `verse`/`idx`
    directly with no extra ref-plumbing needed on the caller's side.
  - `Practice.tsx` rewritten again: manual Record/Stop button removed
    entirely; single "🎙 Start reciting this page" / "Stop listening" toggle
    + live volume bar. `handleSegment(blob)` grades the segment against the
    CURRENT `verse` — pass (content ok, no red word) advances after the
    existing 1.4s delay same as before; fail leaves the reciter on the same
    āyah with an inline "🔁 Not quite — recite this āyah again, still
    listening" prompt, and does nothing else because the recorder is
    ALREADY listening again by the time grading finishes. Deleted the now-
    dead `useRecorder.ts` (fully superseded, no other callers).
  - Validated: pause-detector logic via the node script above;
    `npm run typecheck`/`build` clean; live smoke test confirmed the page
    loads, the Start button appears, and the mic-denied error path (expected
    in this headless environment — no physical mic) degrades gracefully with
    the same message style as the old recorder, no crash, retry available.
  - **NOT YET VALIDATED: real acoustic behavior with an actual reciting
    voice** (silence-threshold tuning, whether 700ms cuts too eagerly/too
    late between real āyahs, whether background noise trips `speechRms`).
    This NEEDS the user testing with a real microphone — flag this clearly
    if they report the auto-cutting feels off, and be ready to retune
    `DEFAULT_PAUSE_CONFIG` in pauseDetector.ts based on their report rather

MAJOR REARCHITECTURE (2026-07-07): word-by-word WINDOW grading, not ayah-by-ayah
===============================================================================
User found a REAL bug in the continuous-recitation design above: if a whole
sūrah is recited fluently with little/no pause between āyahs, the silence-
based segmenter never fires, so ALL the audio piles into ONE segment — which
was still misattributed to whatever āyah the cursor happened to be on
(āyah 1, since nothing had advanced it yet). The fundamental flaw: the old
design ASSUMED "this audio segment IS exactly āyah N" instead of measuring
how far the recitation actually got. User's fix request: correct word-by-word
(not ayah-by-ayah), and render the sūrah like an actual Qur'an book (one
continuous flow), not one boxed row per āyah.

**Backend — sliding window instead of one assumed āyah:**
  - `ground_truth.py`: new `RangeGroundTruth` + `AyahSpan` types and
    `get_range(surah, start_ayah, count)` on BOTH LocalGroundTruth and
    SupabaseGroundTruth — concatenates `count` consecutive āyahs' text into
    one string (offset-adjusted tajweed segments, per-āyah char spans),
    truncating gracefully at the sūrah's end. Verified against real data:
    offsets exactly match text slices; boundary case (asking for 5 āyahs
    starting at 1:6, only 2 exist) correctly returns just those 2.
  - `evaluate.py`: new `evaluate_window(audio, surah, start_ayah, aligner,
    gt_source, count=6, ...)` — aligns the clip against the WHOLE WINDOW's
    text (not one āyah), runs the existing word_score.score_words() over it
    (unchanged — it's already ayah-agnostic, just operates on whatever text
    it's given), then walks the window's āyahs in order computing
    `confirmed_ayahs` = the consecutive prefix of āyahs "recognized enough".
  - **CONFIRM_RATIO tuning — validated on real audio, do not set back to
    "require ALL words":** first attempt required every word in an āyah to
    be content_ok. Tested on REAL correct continuous audio (alafasy 1:1+1:2+
    1:3 concatenated, no pause) — confirmed_ayahs came back EMPTY even though
    the recitation was perfect, because the raw non-Quran-tuned CTC decode
    has a genuine per-word error rate of ~25-40% even on clean correct audio
    (e.g. "ٱلْعَٰلَمِينَ" decoded one letter short) — requiring 100% word
    accuracy per āyah is unrealistic given this baseline noise. Switched to
    CONFIRM_RATIO=0.5 (majority of words content_ok, inclusive) and
    re-verified the SAME real audio: confirmed_ayahs correctly came back
    [1,2,3] (exactly what was recited) and correctly stopped before 4/5/6
    (not recited in that clip, all red). ALSO verified the negative case —
    audio of 1:1 followed directly by 1:3 (āyah 2 SKIPPED) — confirmed_ayahs
    correctly returned [1] only, even though ayah 3's content technically
    appears later in the clip (the consecutive-prefix rule correctly refuses
    to "skip ahead" over the gap). Both directions verified — majority
    threshold is robust, not just permissive.
  - Only `start_ayah`'s muqattaʿāt/basmala CONTEXT is passed to measure_all
    for a window (not per-ayah-in-window) — acceptable v1 simplification, a
    window starting mid-recitation on a muqattaʿāt-opening āyah is rare and
    the effect is scoped to that one rule's grading.
  - `types.py`: new `WindowReport` (surah, start_ayah, end_ayah,
    ayah_spans, confirmed_ayahs, word_scores — each word tagged with its
    owning āyah number via `_ayah_for()`).
  - `server/app.py`: new `POST /grade_window` (surah, start_ayah, file) →
    WindowReport JSON. Window size configurable via `CORRECTION_WINDOW_AYAHS`
    env var (default 6). Verified live via curl against the real running
    server — output exactly matches the direct-function-call tests above.
  - Tests: +3 in tests/test_correction.py (majority-threshold boundary
    inclusive, genuine-miss still stops the prefix, per-word āyah tagging) —

SECOND MAJOR REARCHITECTURE (2026-07-08): "sūrah = one paragraph", no cursor at all
===============================================================================
User's own words: "our method of analysing is not optimal, it's not giving
the right output — we need to deal with Qur'an like every sūrah is just a
paragraph, that's why you can analyse it without needing to navigate between
āyahs." This came right after the window/cursor design above (confirmed_
ayahs, resume_ayah rescue) — that design was a real improvement but still
had a CLIENT-TRACKED CURSOR as its foundation, and inherited a whole class of
"what if the cursor gets out of sync with reality" bugs by construction.

**The redesign: the SERVER locates every clip within the WHOLE sūrah from
its content — no `ayah`/`start_ayah` parameter at all.** Client just says
"here's a clip, here's which sūrah" and gets back which āyah(s) it
corresponds to, graded. No cursor to track, no cursor to get stuck.

Backend, in build order (several dead ends along the way — kept here since
future work will hit the same tradeoffs):

  1. **Split the aligner into decode()/align_from_decode()** (aligner.py).
     Locating a clip within a whole sūrah, then grading precisely, needs TWO
     different text scopes (whole sūrah for locating, one identified āyah
     range for grading) from the SAME audio — but the model forward pass
     (expensive) must only run ONCE. `decode()` does the forward pass +
     greedy CTC decode and returns a `DecodeResult` (cached logits);
     `align_from_decode()` reuses those cached logits to forced-align against
     ANY text, repeatably, with no further model calls. `align()` kept as a
     decode()+align_from_decode() convenience wrapper for backward compat
     (evaluate()/evaluate_window() unchanged). Verified byte-identical output
     vs the old single-call align() on real audio.

  2. **Localization attempt #1 — word-level** (word_score.matched_ref_range,
     since removed). Reused the existing word-level align_words DP against
     the whole sūrah's word list. FOUND NOT ROBUST: a real, CORRECTLY-recited
     1:5 clip decoded with SCRAMBLED word boundaries (the CTC "|" delimiter
     token mispredicted, merging/splitting words wrong) even though the
     underlying LETTERS were fine — word-level matching found ZERO matches
     for content that was actually right. Root cause: word-level matching is
     fundamentally sensitive to the ASR's word-boundary predictions, which
     aren't reliable enough for this. REMOVED entirely (function + its 3
     tests) in favor of #3.

  2b. **content_check.locate_best_span — CHARACTER-level instead of word-
     level.** Reuses char_error_rate's consonant-skeleton comparison
     (Phase 0, already proven robust to word-boundary noise since it doesn't
     use words at all). First version: try every consecutive-āyah span (1..6
     āyahs) starting at every position, score each with full CER, keep the
     best. CORRECT in every test (including the word-boundary-scrambled 1:5
     case) but SLOW: measured 41s on a single long āyah (Āyat al-Kursī, ~52s
     recited) within a long sūrah (Al-Baqara, 286 āyahs) — O(n×max_span) full
     Levenshtein calls is a lot of duplicated work for a long sūrah.

  3. **Localization attempt #2 — Smith-Waterman local alignment.** ONE
     O(len(decoded)×len(sūrah)) DP pass instead of many separate
     comparisons — fast in theory. FOUND TWO NEW PROBLEMS: (a) still ~20s+ in
     pure Python for a long sūrah (interpreter overhead on a large matrix,
     no numpy used); (b) a SHORT āyah (2:1, "الم" — Alif-Lām-Mīm, 3 letters)
     matched a WRONG position elsewhere in Al-Baqara by pure chance — local
     alignment has no concept of "this match is suspiciously short/weak", so
     a tiny needle can score decently almost anywhere in a long haystack.
     REMOVED — replaced by #4.

  4. **Localization attempt #3 (final) — adaptive two-stage, in
     content_check.py.** Kept #2b's PROVEN correctness, fixed its speed:
       - SHORT decoded clip (< SHORT_HYP_CHARS=12 normalized chars, e.g. the
         "الم" case): skip any prefilter, run the exact search over every
         candidate — cheap regardless of sūrah length when hyp itself is
         short (this is exactly the case where a cheap prefilter has no
         signal to offer anyway — a 3-letter query has ~2 bigrams total).
       - LONG decoded clip: a CHEAP bigram-overlap prefilter (precomputed
         per-āyah, O(n×max_span) not O(n×max_span²) — an incremental/capped
         accumulation, not re-normalizing overlapping windows from scratch)
         ranks all candidates; only the top_k=6 best-looking ones get the
         EXPENSIVE exact comparison.
     Verified: real long-āyah case (Āyat al-Kursī, full 52s) dropped from
     41s → ~20s for a FULL clip (see below for why this doesn't matter in
     practice) and a REALISTIC ~6s partial clip → 1.5s. Short-āyah case
     (2:1) correctly locates ayah 1 (was landing on a wrong āyah with both
     earlier attempts).

  5. **A SEPARATE real bug found along the way — partial-recitation length
     bias.** A short clip covering only the OPENING of a long āyah (e.g. 6s
     of Āyat al-Kursī's 52s) was locating a SHORT, WRONG āyah (2:163, shares
     "لا إله إلا هو" but not "الحي القيم") instead of the correct long one
     (2:255) — root cause: whole-window CER (`edit_distance/len(ref)`)
     counts the āyah's entire UNRECITED remainder as "error", so a short
     clip structurally favors any accidentally similarly-SHORT wrong āyah
     over the correct long one. Fixed with `_prefix_aware_cer` — compares
     the clip against a PREFIX of the candidate window sized to the clip's
     own length (with slack), not the whole window. Had to fix this in BOTH
     the final CER stage AND the bigram prefilter (capping the prefilter's
     window length the same way) — fixing only one still let the correct
     long āyah get filtered out before the final stage ever saw it. Verified
     on the real Āyat al-Kursī partial clip (now correctly locates 255) and
     a synthetic unit test (careful this time to use non-overlapping fixture
     words — an earlier version of the test accidentally shared a word
     between its two fixture āyahs and gave a false failure).

  6. **evaluate_clip() reuses locate_best_span's score directly** as
     `content_cer`/`content_status`, instead of re-running check_content() on
     the whole identified sub-text — that would have reintroduced exactly
     the partial-recitation bias #5 just fixed. `locate_best_span` now
     returns `(ayah_from, ayah_to, cer)`, not just the range.

  7. **`LocalGroundTruth` performance fix — unrelated to the above but
     found because of it.** `get()`/`get_range()` used to call
     `extractor.iter_segments()` once PER RULE PER ĀYAH (18×N calls), and
     each call RE-SCANS THE ENTIRE ANNOTATIONS JSON FILE FROM DISK. For a
     single āyah this was slow-but-tolerable (~18 scans); for `evaluate_clip`
     fetching a WHOLE sūrah (even just Al-Fātiḥa's 7 āyahs = 126 scans) it
     was measured at ~15s of pure I/O overhead PER REQUEST — the actual
     model decode was only ~2s. Fixed with a lazy-built, one-time in-memory
     index (`_index()`, built via a single streaming pass on first access,
     cached for the process's lifetime) — dropped to ~0.1-0.3s regardless of
     how large the requested range is. This is why the "41s" and "20s"
     numbers above look so bad relative to later measurements — the ground-
     truth I/O bug was compounding the localization algorithm's own slowness
     for a while before being isolated and fixed separately.

  8. **New endpoint `POST /grade_clip`** (surah, file) → `ClipReport`
     (`located`, `ayah_from`, `ayah_to`, `content_status`, `word_scores`
     tagged per-āyah). `/grade_window` and `/grade` kept functional
     (unused by the frontend now, but harmless to leave — evaluate()/
     evaluate_window() are still valid, simpler entry points for anything
     that DOES already know which āyah it wants).

Frontend — `Practice.tsx` rewritten a third time, this time much SIMPLER
than either prior version: no `cursorAyah`/`confirmed_ayahs`/`resume_ayah`
state or branching at all. `handleSegment` just calls `gradeClip(surah,
wav)` (no āyah argument) and merges whatever word_scores come back, tagged
by their OWN āyah number, directly into `wordsByAyah` — every returned word
genuinely belongs to a correctly-IDENTIFIED range, so (unlike the window
design) there's no need to filter out "not-yet-reached" speculative āyahs
either. `highlightAyah` replaced `cursorAyah` as a PURELY COSMETIC "which
āyah to softly highlight" value, set to whatever the latest response
identified — it is NOT an input to grading anymore, just a display detail.
Rolls to the next sūrah when the located range reaches the sūrah's last āyah
with a passing grade. `lib/correction.ts`: added `gradeClip`/`ClipReport`,
removed `gradeWindow`/`WindowReport` (dead — Practice.tsx was their only
caller), renamed `WindowWordScore` → `AyahTaggedWordScore` (shared shape,
name no longer tied to the now-removed window concept; `GradedSurah.tsx`
updated to match).

Validated: 46/47 Python tests (7 new: locate_best_span × 5 scenarios +
evaluate_clip × 2, using fresh Fake aligner/ground-truth fixtures mirroring
the existing test conventions); `npm run typecheck`/`build` clean; live

Āyat al-Kursī located correctly at realistic (~6s) clip length.

**One remaining KNOWN, PRE-EXISTING limitation, not a new bug:** muqattaʿāt

FOLLOW-UP FIX (2026-07-08, user's FIRST real-mic test): word_score.py still
used strict word-level matching, reproducing the exact bug locate_best_span
was already fixed for
-------------------------------------------------------------------------------
User shared a screenshot of their first real recitation of Al-Fātiḥa in
paragraph mode: most of āyahs 3, 5, 6, 7 showed red ("word not recognized")
despite what looked like a correct recitation. Root cause: `locate_best_span`
(above) was deliberately rewritten to compare CHARACTERS, not words, because
the CTC greedy decode's word-delimiter predictions can scramble word
boundaries even on CORRECT audio — but `word_score.py`'s per-word GRADING
(`align_words`/`score_words`, which is what actually produces the red/yellow/
green colors the user sees) was never updated and still required an EXACT
string match (after `normalize_arabic`) between a decoded word and a
reference word. A single scrambled boundary or a single ASR-misheard letter
anywhere in a word was enough to flag that whole word red, and because
`align_words` is a Levenshtein/backtrace WORD-level DP, one bad match could
throw off the alignment of everything after it — a cascade, matching exactly
what the screenshot showed (long runs of red rather than isolated words).

**Fix (word_score.py):** replaced the DP's binary 0/1 substitution cost with
a continuous per-word CHARACTER-error-rate cost (`_word_sub_cost`, reusing
`content_check._levenshtein`) — two words are still "the same word" if they're
close (small ASR letter slip, shifted boundary), but a genuinely different
word (high CER) still costs close to 1.0, same as before. `WORD_CONTENT_
MISMATCH_CER = 0.5` gates whether a diagonal (aligned) pair counts as
`content_ok`. Backtrace changed from re-deriving the path via float `==`
comparisons to storing explicit back-pointers during the forward DP pass
(robust against float-equality pitfalls the fuzzy costs would otherwise
introduce). `score_words`'s interface (and all its callers) unchanged — only
`align_words`'s internal cost function changed, still returns `List[bool]`.

**Validated on real audio** (script kept at `.build_tmp/probe_word_score_
fix.py`): ran `evaluate_clip` on husary's real recording of EACH āyah of
Al-Fātiḥa individually (reproducing the screenshot's scenario — one segment
per āyah). Before this fix, per-letter ASR noise alone (e.g. āyah 4 decoding
"مالث يون الدين" for "مَالِكِ يَوْمِ الدِّينِ" — last letter of two words
misheard) would have flagged those words red under exact matching. After the
fix: **0 red words on āyahs 1–6, 1 red word on āyah 7 (out of 33 total
words)** — the single remaining red is a genuine two-word boundary collapse

THIRD FIX (2026-07-08, same day): word-level grading rebuilt on GLOBAL
character alignment — no word-splitting at all, ever
-------------------------------------------------------------------------------
User's second screenshot (after the fuzzy-CER fix above) showed real
improvement (āyahs 1, 2, 3, 6 fully green) but āyahs 4, 5, 7 were still
mostly red despite what sounded like correct recitation. User's instruction:
"try different method to make it the most reliable possible without making
it don't recognize mistakes" — i.e. don't just loosen thresholds further
(that risks silently accepting real mistakes), find the actually-robust
approach.

Investigated with a purpose-built probe
(`.build_tmp/build_continuous_fatiha.py` + `.build_tmp/probe_continuous_
fatiha.py`, husary's real Al-Fātiḥa audio concatenated into one continuous
50s clip, decoded as a single pass): the decoded text came back as
**"بِسْمِ اللَّه الرَّحمَنِ الرَّحيِالْحَمْدُ لِلَّهِ رَبِّ الْعالَمِمِ
الرَّحْمَنِ الرَّحِيمِمَالِكِ يَومِ الدِّيمِإِيَا كَنَعْبُدُوا..."** — at
EVERY single āyah boundary, the CTC's word-delimiter "|" token vanished
entirely, fusing the end of one āyah directly into the start of the next
with ZERO space ("الرحيم" + "الحمد" → "الرَّحيِالْحَمْدُ"). This is far more
severe over a long continuous decode than the isolated-word slips the
previous fix targeted — the fuzzy per-WORD DP still needs `decoded_text.
split()` to produce roughly-word-shaped tokens to match against, and a
2-word fusion produces one token that doesn't resemble EITHER real word well
under any reasonable per-word threshold. This explained exactly why red
clustered right at āyah boundaries (4/5, 5/6, 6/7 junctions).

**Fix: stop splitting decoded text into words at all.** `word_score.py`
rebuilt around a single GLOBAL character-level Levenshtein alignment (with
backtrace) between the normalized reference text and the normalized decoded
text — the same "character, not word" philosophy `locate_best_span` already
used for localization, now applied to grading too. For each reference word,
content_ok is derived from what FRACTION of its own letters found an
identical letter in the decoded text, via that ONE alignment — never by
looking for a decoded "word" boundary. A genuinely fused pair of words still
has each word's own letters sitting compactly together in the decoded
stream, so this survives boundary loss that would sink any word-splitting
approach by construction.

**A real new failure mode surfaced while writing regression tests for this**
(caught before it ever reached real audio): a GLOBAL alignment with no
locality constraint lets a very SHORT reference word "match" by pure chance
— e.g. testing 112:1's text against 1:1's actual audio (the canonical "wrong
ayah" regression case from Phase 1), the word "أَحَدٌ" (aḥad, 3 letters)
came back falsely "recognized" because a stray ا and ح happened to occur 4
characters apart inside the unrelated word "الرحيم" elsewhere in the
decode — 2 of 3 letters "found", passing a plain ratio threshold, despite
having nothing to do with the actual word. Fixed with a COMPACTNESS check
independent of word length: `gap = span_of_matched_positions -
count_of_matched_letters` (`WORD_GAP_SLACK = 1`) — a genuinely-present word,
even with one missed letter or one stray inserted letter, keeps its matched
letters clustered tightly together in the decode; a coincidental match on
unrelated text does not. This single gap-based signal turned out to
correctly separate ALL three cases found during development: the fake
"أَحَدٌ" match (gap 2 → rejected), a genuine single-letter ASR slip
("مَٰلِكِ" decoded as "مالث", last letter wrong, gap 0 → still accepted),
and a genuine stray-letter insertion ("اهدنا" decoded "اهدينا", gap 1 →
still accepted) — no word-length-based special-casing needed once the right
invariant (compactness, not just count) was found.

FOURTH FIX (2026-07-08, same day): word offsets weren't rebased per-āyah —
a correctly-graded word could render as plain black text
-------------------------------------------------------------------------------
User's third screenshot (after the THIRD FIX above) showed a striking, very
specific anomaly: āyah 4's progress dot was GREEN ("pass") but its text
("مَٰلِكِ يَوْمِ ٱلدِّينِ") rendered completely UNCOLORED — plain black, no
underline, as if never graded at all — while neighboring āyahs colored fine.
A dot showing "pass" REQUIRES that āyah's words to have been graded
successfully at some point (the status is computed directly from the same
word objects that get stored for rendering), so this could only be a
rendering-layer bug, not a grading one.

Root cause, found in `types.py`: `ClipReport.to_dict()` (and the older,
now-unused `WindowReport.to_dict()`) tags each `WordScore` with which āyah it
belongs to (`_ayah_for`), but never re-bases its `start_idx`/`end_idx` — they
stay relative to the START OF THE WHOLE LOCATED RANGE (`evaluate_clip`'s
`sub_text`, which concatenates every āyah the clip was matched against), not
to that word's OWN āyah's text. `GradedSurah.tsx` on the frontend, however,
treats `start_idx`/`end_idx` as offsets into `v.text` — that SINGLE verse's
own text alone. This only coincidentally works when a clip locates to
EXACTLY one āyah (`ayah_from == ayah_to`) — sub_text and that āyah's own
text are then the same thing, offset 0 either way, which is why every
earlier isolated-per-āyah test (both real audio probes and the unit tests)
never caught it. The moment a clip's located range spans 2+ āyahs, every
āyah AFTER the first has a start_idx offset by however long the preceding
āyah(s) in that range were — comfortably past the length of its own short
verse text — so the render loop (`for i = start_idx; i < end_idx; i++`)
never touches any of the CORRECT indices (0..v.text.length) and the word
silently never colors, even though it graded fine.

**Fix:** `ClipReport._word_dict()` (new helper, used by `to_dict()`) now
subtracts that word's OWN āyah's start offset (already available in
`ayah_spans`, which stores per-āyah boundaries within the located range)
before sending `start_idx`/`end_idx` to the frontend — every word the client
receives is now offset from the START OF ITS OWN ĀYAH, matching exactly what
`GradedSurah.tsx` already assumed. Applied the identical fix to the legacy
`WindowReport.to_dict()` for consistency, even though nothing calls
`/grade_window` from the frontend anymore.

Validated: new unit test `test_evaluate_clip_to_dict_rebases_offsets_per_ayah`
(a clip located across 2 fake āyahs, asserting every word's serialized
start_idx/end_idx stays within ITS OWN verse's length) — suite 49/50 (same
pre-existing pytest-only failure). Real audio: a genuine 3-āyah husary clip
(1:1+1:2+1:3 concatenated, `.build_tmp/probe_multiayah_offsets.py`) —
every word from āyah 2 and 3 (the ones that would have been broken before)
now serializes with start_idx/end_idx correctly bounded within its own
verse's length. Restarted the correction server with this fix.

FIFTH CHANGE (2026-07-08, same day): sliding-window "live" grading —
user-requested rearchitecture of the mic capture layer, not a bug fix
===============================================================================
User reported the app "not coloring the quran live when I'm reciting" — the
existing design (`useAutoRecorder`) records a chunk (cut on a detected pause,
or forced every 4s), THEN sends the WHOLE chunk for grading, so there's
always a multi-second gap between saying something and it coloring. Asked

**Honest constraint surfaced to the user before building anything:**
wav2vec2-large-xlsr-53 on CPU (no GPU in this setup) takes ~1.5-5s to decode
even a single few-second clip (measured throughout this session). Sub-second,
literal word-by-word highlighting AS you speak is not achievable with this
model on CPU — no frontend architecture change fixes that, it's raw compute
time, and there's no usable small/fast Arabic CTC model to fall back to for a
cheap preview pass (already investigated and rejected during Phase 4
calibration work, 2026-06-30: the only available small model has an
English-only vocab). What IS achievable and was proposed instead: a SLIDING
WINDOW graded on a fixed ~1.7s timer instead of waiting for a pause or a hard

`useAutoRecorder` in `Practice.tsx` only (NOT in `Drills.tsx`, which still
uses the pause-cut design for isolated per-rule examples — out of scope,
untouched):
  - Needs raw PCM, not MediaRecorder's encoded chunks — a sliding window has
    to start at an arbitrary sample, and only the FIRST chunk of a
    MediaRecorder stream carries the container header (same constraint
    `useAutoRecorder`'s docstring already documents). Capture goes through a
    `ScriptProcessorNode` (deprecated but simple and universally supported;
    an AudioWorklet would need its own module file for no real benefit at
    this scale) feeding a ring buffer of Float32 chunks, routed through a
    silent (`gain=0`) node to the destination so the mic input is never
    played back out loud (ScriptProcessorNode needs SOME destination
    connection to fire its callback in some browsers).
  - Every `INTERVAL_MS` (1700ms), if no grading call is already in flight
    (`gradingRef` gate — SKIPS a tick rather than piling up concurrent CPU
    decodes, since the interval is deliberately close to the model's own
    per-clip latency and concurrent calls would only slow each other down
    without a GPU to parallelize on), slices the last `WINDOW_MS` (3200ms) of
    buffered samples, skips it if it's pure silence (RMS check, saves a
    wasted decode call), and hands it to the caller already resampled.
  - New `app/src/lib/wav.ts` export `pcmFloat32ToWav16kMono(samples,
    sourceSampleRate)` — factors the existing `blobToWav16kMono`'s
    resample-to-16kHz-mono step (`resampleTo16kMono`, via an
    `OfflineAudioContext` render) out into a shared helper, so the new path
    skips only the `decodeAudioData` step (irrelevant for raw PCM already in
    hand) while reusing the exact same, already-proven resampling code.
  - `Practice.tsx`: `handleSegment` renamed `handleWindow`, now receives an
    ALREADY-encoded 16kHz WAV blob directly (no more `blobToWav16kMono` call
    in the component — the hook does it), debug-log wording and UI copy
    updated to describe rolling windows instead of pause-triggered cuts.
    Because grading is now stateless per rolling window exactly like before
    (`evaluate_clip`/`locate_best_span` needed no server changes at all),
    `wordsByAyah`'s merge-and-replace-per-āyah logic naturally self-corrects
    as later, fresher (and typically more complete) windows overwrite earlier
    partial ones for the same āyah — no new merge logic needed.

SIXTH FIX (2026-07-08, same day): rolling windows caused visible green→red
flicker — sticky, monotonic word merge
-------------------------------------------------------------------------------
User's fourth screenshot (first real test of the rolling-window design) —
described the problem precisely: "sometimes it makes the words green than it
changes it to red" and asked for the app to treat detection like writing the
recitation down as a paragraph rather than re-deciding each āyah from
scratch every time.

Root cause: each rolling window is graded completely independently and
STATELESSLY (by design — that's what makes `evaluate_clip` robust to begin
with). But `Practice.tsx`'s merge was `setWordsByAyah(prev => ({...prev,
...grouped}))` — for any āyah touched by a response, the ENTIRE word array
was replaced wholesale. Since overlapping ~3.2s windows re-decode much of the
SAME audio repeatedly (the window slides forward only ~1.7s at a time, so
~45% of each window's audio was already covered by the previous one), a
later window's slightly different framing of the SAME word (e.g. starting or
ending mid-syllable relative to the previous window) can occasionally
mis-grade something the previous window graded correctly — and because the
whole āyah's array got replaced, that ONE noisy re-grade was enough to flip
an already-correct word from green back to red on screen.

**Fix:** word-level STICKY, MONOTONIC merge (`handleWindow` in
`Practice.tsx`), matched by `start_idx` (reliable now that offsets are
per-āyah-local — see the FOURTH FIX above; this fix depended on that one).
For each word, if the PREVIOUS result said `content_ok=true` and the NEW
result says `content_ok=false`, keep the OLD (green) result — a later noisy
re-grade can never downgrade a word that was already confirmed. A fresh
green DOES overwrite an old red (upgrades are real progress: the reciter
finished the word, or a later window's framing simply caught it better).
Tracked via a `wordsByAyahRef` mirror (read/written synchronously inside
`handleWindow`, since React state itself updates asynchronously and the next
rolling-window response can't wait a render cycle to see the merged truth).
`ayahStatus`'s pass/needs_work ratio is computed FROM the same sticky-merged
words, so it inherits the same monotonic guarantee automatically — no
separate status-level special-casing needed, since a fixed word count with
only-ever-upgrading individual verdicts means the aggregate ratio can only
stay the same or improve over successive rounds.

**A second, related bug fixed in the same pass:** `memorization.
recordReview` (the SM-2 spaced-repetition tracker) was being called on
EVERY rolling-window response that touched a given āyah — with āyahs now
getting re-confirmed every ~1.7s while being recited, a single real
recitation of one āyah could fire `recordReview` 3-5+ times in a row,
inflating its review history as if it had been separately reviewed that many
times. Fixed with a `recordedAyahsRef` set (reset per sūrah) — records each
āyah into the memorization tracker only the FIRST time it's graded per
session, matching the granularity the original pause-cut design had
(roughly one grading event per āyah).

Both refs (`wordsByAyahRef`, `recordedAyahsRef`) are reset alongside the
existing per-sūrah state reset effect. Validated: `npm run typecheck` and
`npm run build` clean. Browser preview blocked again by the same unrelated
sandbox proxy issue as the FIFTH CHANGE (raw HTTP connection refused before
any JS runs — confirmed independent of this code, and moot anyway since real
mic capture can't be exercised in this sandbox regardless).

SEVENTH FIX (2026-07-08, same day): sūrah advanced before the reciter
finished — repeated phrase ambiguity + no gapless-confirmation guard
-------------------------------------------------------------------------------
User reported the app advanced to the next sūrah before they'd finished
reciting Al-Fātiḥa, and correctly diagnosed the mechanism themselves:
"الرحمن الرحيم" appears TWICE in Al-Fātiḥa — once as the tail of āyah 1
("بسم الله الرحمن الرحيم") and again as the ENTIRETY of āyah 3. Since
`locate_best_span` is deliberately stateless (searches the whole sūrah fresh
every time, no memory of where the reciter was a moment ago — see the
SECOND MAJOR REARCHITECTURE above), a short phrase that genuinely repeats
elsewhere in the same sūrah gives the search a real ambiguity to resolve with
NO positional information to break the tie. If a window's match ever locks
onto the WRONG occurrence (or a chain of borderline matches drifts forward),
`ayah_to` can jump further ahead than the reciter actually reached —
including, worst case, appearing to reach the sūrah's last āyah and
triggering the "finished, roll to next sūrah" transition prematurely.

**Two complementary fixes, addressing both ends of the problem:**

1. **Backend — `near_ayah` soft proximity hint (`content_check.
   locate_best_span`, threaded through `evaluate.evaluate_clip` and the
   `/grade_clip` endpoint's new optional `near_ayah` form field).** When
   multiple candidates score within `tie_epsilon` (0.05) of the best CER,
   the one CLOSEST to `near_ayah` wins the tie — but a candidate that's
   CLEARLY better (outside that epsilon) always wins regardless of distance,
   so this can never override real content evidence, only resolve genuine
   near-ties. Deliberately NOT a repeat of the old cursor design's mistake
   (a hard constraint that could get "stuck") — it's advisory only.
   `Practice.tsx` sends its current `highlightAyah` as this hint on every
   `gradeClip` call (`lib/correction.ts`'s `gradeClip` gained an optional
   third `nearAyah` param). Validated: new unit test
   `test_locate_best_span_near_ayah_breaks_tie` (two āyahs with IDENTICAL
   text — a clean, deliberately-constructed genuine tie — confirms the hint
   correctly picks whichever is closest); real husary audio of the ambiguous
   phrase itself (`.build_tmp/probe_near_ayah.py`) confirms the hint does
   NOT interfere with an unambiguous match (a clean recitation of "الرحمن
   الرحيم" alone locates to āyah 3 regardless of the hint, since its CER is
   unambiguously best there — this specific isolated case was never actually
   tied in practice, since āyah 1's candidate needs the preceding "بسم الله"
   that isn't in the clip; the REAL ambiguity this guards against arises from
   noisier/messier window framing in an actual continuous rolling-window
   session, harder to construct as a clean isolated audio test).

2. **Frontend — gapless-confirmation guard on the sūrah-advance trigger**
   (`Practice.tsx`, directly matching the user's own words: "if it skips it
   stop"). Even with the hint above reducing HOW OFTEN a bad jump happens, it
   doesn't guarantee it can never happen — so the "roll to the next sūrah"
   transition now ALSO requires that every earlier āyah has ALREADY been
   separately confirmed (`ayahStatus[...] === "pass"`) before trusting that
   the located last āyah means the sūrah is actually finished. A new
   `ayahStatusRef` mirrors `ayahStatus` synchronously (same reason as
   `wordsByAyahRef`) so this check can run within the same async
   `handleWindow` call that decides whether to advance. Reset alongside the
   other per-sūrah refs.

Validated: `npm run typecheck`/`build` both clean; Python suite 50/51 (new
test added, same pre-existing pytest-only failure). Restarted the correction

EIGHTH FIX (2026-07-08, same day): prefix/suffix CER used a guessed slack
length that could swallow the wrong amount of the candidate window —
replaced with a proper free-end-gap alignment DP
-------------------------------------------------------------------------------
Reciting ONLY Al-Fātiḥa 1:1 ("بسم الله الرحمن الرحيم") got the server to
locate 1:3 instead — confirmed by the user ("here I just recited the first
ayah"), matching the mechanism flagged in the SEVENTH FIX: a rolling window
holding only the last ~3.2s of audio can scroll PAST "بسم الله" once enough
time has passed, leaving only "الرحمن الرحيم" — which is 1:3's entire text,
a perfect match — while 1:1's own text needs "بسم الله" that's no longer in
the clip. Investigating WHY the SEVENTH FIX's `near_ayah` tie-break didn't
catch this revealed the tie wasn't actually happening: `_suffix_aware_cer`
(added same day, see SEVENTH FIX/SUFFIX section above) sized its comparison
window via `min(len(window), int(len(hyp)*1.3)+5)` — a guessed slack length
carried over unchanged from the ORIGINAL `_prefix_aware_cer`. For a short
single-āyah candidate close in length to the clip itself (1:1's full text is
only ~19 normalized characters, hyp "الرحمن الرحيم" is 12, and the slack
formula computes a 20-character target), that guessed length EXCEEDED the
whole candidate window — degrading the "suffix" comparison back into a
WHOLE-WINDOW comparison, unable to trim out "بسم الله" at all, scoring 1:1
just as badly as before the SEVENTH FIX (confirmed via direct debugging:
prefix CER and suffix CER came out IDENTICAL, 0.368, both accidentally
comparing against the same full 19-char window).

**Root cause: guessing a fixed comparison-window length by formula is
inherently fragile whenever the candidate window's own length is close to
the clip's length** — there's no slack constant that both (a) tolerates a
few characters of genuine ASR insertion noise and (b) reliably trims out
exactly the right amount of "extra" content when that extra content
(here, "بسم الله", ~7 characters) is smaller than the slack margin needed
for (a). A synthetic regression test written to lock in the fix
(`test_locate_best_span_tail_of_longer_ayah_ties_with_shorter_repeat`) caught
this immediately — it failed even though the SEVENTH FIX's logic was
otherwise sound, which is exactly why it's valuable to write the test before
declaring a fix done rather than trusting reasoning alone.

**Fix: stop guessing a comparison-window length at all.** `_prefix_aware_cer`
/`_suffix_aware_cer` (slice-then-Levenshtein) replaced by `_prefix_fit_cer`/
`_suffix_fit_cer` — a proper free-end-gap edit-distance DP:
  - `_prefix_fit_cer(hyp, window)`: standard Levenshtein DP with `dp[0][j]=j`
    (hyp anchored to window's own START) but the ANSWER is `min` over every
    `dp[len(hyp)][j]` instead of just `dp[len(hyp)][len(window)]` — i.e. the
    DP itself finds the best-fitting boundary where hyp "ends" within
    window, with window free to extend further at NO cost. No slack constant
    to guess wrong.
  - `_suffix_fit_cer(hyp, window)`: `_prefix_fit_cer` called on BOTH strings
    REVERSED — edit distance is invariant under simultaneous reversal, and
    "hyp's end anchored to window's end, window free on the left" is exactly
    "hyp's start anchored to window's start, window free on the right" once
    reversed. One DP implementation, no second one to keep in sync.
  - Both anchor ONE end of hyp to the corresponding end of window (unlike
    full local/Smith-Waterman alignment, which was already rejected earlier
    this session for letting a short hyp match ANYWHERE with no penalty for
    match weakness — a muqattaʿāt-scale risk this deliberately avoids by
    still requiring hyp's start-or-end to align with window's start-or-end,
    not float freely in the middle).
  - `locate_best_span` takes `min(_prefix_fit_cer(...), _suffix_fit_cer(...))`
    per candidate, same as before, just with the more robust scoring
    underneath. The bigram prefilter (for long clips) already got its own
    prefix+suffix-aware fix as part of the SEVENTH FIX and needed no further
    change here.

Validated: the new regression test now passes; full suite 50/52 (2 new
tests this round, same pre-existing pytest-only failure). Real audio — a
genuinely truncated husary 1:1 clip, cut at 2.3s to simulate exactly what a
rolling window would hold after scrolling past "بسم الله"
(`.build_tmp/probe_tail_of_ayah1.py`): **locates correctly as 1:1 even with
NO hint at all** (cer=0.143, the residual reflecting that the manual 2.3s
cut point also clipped a bit into "الرحمن" itself); with `near_ayah=3`
explicitly, it correctly flips to 3:3, proving the tie-break mechanism now
actually engages when the ambiguity is real. Re-ran the broader per-āyah
husary regression probe (`.build_tmp/probe_word_score_fix.py`) — identical
results to before this fix (2 red words total across all 7 āyahs), confirming
no regression from replacing the CER metric. Restarted the correction
server.

NINTH FIX (2026-07-08, same day): the longest āyah showed red immediately
and "didn't let me finish reciting" — unspoken words graded as wrong
-------------------------------------------------------------------------------
User: "in the last ayah and the longest one in fatiha it directly show in
red and don't let me finish reciting" — Al-Fātiḥa 1:7 (9 words, by far the
longest) turning red before the reciter had said the whole thing. User's own
diagnosis, unprompted: "I think the problem is that when you check you pass
all the audio but the recitor will speak word by word" — exactly right.

Root cause: `evaluate_clip`'s `sub_text` for a located single-āyah range is
that āyah's WHOLE text, and `score_words`'s per-word grading used a GLOBAL
(fully-consuming, both ends anchored) character alignment between the
decoded clip and that whole text. For a rolling-window clip that only
covers the FIRST few words of a long āyah still being recited, the global
alignment is FORCED to "explain" the entire remaining text somehow — it does
so via deletions, which look identical to "wrong word" to the existing
red/green logic. The trailing, simply-not-yet-spoken words showed red before
the reciter had even reached them.

**Fix, in three layered passes** (each one found a real problem the
previous pass didn't fully solve — validated against REAL truncated Al-Fātiḥa
1:7 audio at every step, not just synthetic tests):

  1. **Exclude unreached words instead of grading them red.** New
     `_reached_bound(hyp, ref)` in `word_score.py` — a free-TRAILING-gap
     alignment DP (hyp anchored to ref's start, ref free to extend past hyp
     at zero cost; same shape as `content_check._prefix_fit_cer`, just
     returning the ARGMIN position instead of the cost) finds how far into
     the āyah the decode's content plausibly reaches. A word starting more
     than `NOT_REACHED_SLACK` (4 normalized chars) past that boundary is
     OMITTED from `score_words`'s returned list entirely — not marked red —
     so it renders exactly like a word that's never been graded (neutral),
     not like a mistake. The word immediately following the reached
     boundary is deliberately left un-excluded: from a single clip there's
     no way to tell "not yet said" from "recitation genuinely stopped
     here", and the existing `test_score_words_catches_missing_word_amid_
     fusion` regression test already requires that adjacent case to still
     read as a real mismatch — this fix is specifically about the FAR tail,
     which is unambiguous.

  2. **`_reached_bound` itself was fooled by coincidental scattered matches
     on real audio.** First real-audio test (a genuine 3-second truncation
     of husary's 1:7) showed NOTHING got excluded — `_char_align_matched`'s
     GLOBAL alignment (used to compute where matches occurred) is forced to
     explain the ENTIRE 43-character reference even when the decode is only
     14 characters, and while doing so it can pick up isolated, coincidental
     common-letter matches scattered far into the "padding" it's forced to
     traverse — the raw "furthest matched position" scan came out at
     character 32 of 43, nowhere near where the decode's real content
     actually ended (~14). Fixed by computing `reached_bound` via the
     free-trailing-gap DP (immune to this — it's never forced to explain
     content beyond what hyp can account for) INSTEAD OF scanning
     `_char_align_matched`'s raw output for this purpose.

  3. **Even with the correct boundary, individual words within the reached
     region still graded wrong on real audio.** Second real-audio pass:
     "ٱلَّذِينَ" (clearly present in the decode) still showed red. Root
     cause: `_char_align_matched` was still being run against the FULL
     43-character reference for the actual per-word grading, not just for
     finding the boundary — with hyp only 14 characters, the DP's globally
     cheapest way to "explain" all 43 characters didn't have to route
     through a clean, intuitive alignment of the real words, since many
     different paths tied for the same total cost. Fixed by truncating the
     reference to `ref_norm[:reached_bound + 1 + NOT_REACHED_SLACK]`
     BEFORE running the detailed per-word alignment — hyp now aligns
     against a similarly-sized reference, matching the actually-spoken
     words cleanly instead of arbitrarily.

  Two more bugs surfaced and fixed by the unit tests written alongside this
  (before further real-audio testing was even needed):
  - `_reached_bound`'s tie-breaking picked the SMALLEST position achieving
    the minimum edit cost, not the largest — several trailing positions
    routinely tie once hyp is "fully spent" (extra reference characters cost
    nothing either way past the true match point), and picking the smallest
    silently under-credited how far hyp actually reached. Caught by
    `test_score_words_substitution_and_deletion` (a clean word DELETED in
    the middle, "بسم [الله] الرحيم", tied at equal cost for stopping right
    after "بسم" vs continuing through "الرحيم" — picking the smaller one
    wrongly excluded "الرحيم", which the decode had genuinely matched).
    Fixed: prefer the LARGEST tied position.
  - Basmala-prefix stripping (`_strip_basmala_prefix`) broke `reached_bound`
    entirely for sūrah 112 (and similar) — the removed prefix is a DATA
    ARTIFACT (present in the text column, never in the actual audio), so
    anchoring the free-trailing-gap DP to `text` index 0 (the basmala's own
    start) made a decode that matched 112:1 perfectly still look like it had
    "reached" nothing (the basmala obviously doesn't match at all), excluding
    every real word. Caught immediately by the pre-existing `test_score_
    words_strips_basmala_prefix_on_ayah1` regression test. Fixed: anchor
    `reached_bound` to the position of the FIRST SURVIVING word (post-strip),
    not raw text index 0.

ELEVENTH FIX (2026-07-08, same day): mid-āyah rolling-window clips graded
against the WRONG part of the reference — reached-region was prefix-only
-------------------------------------------------------------------------------
Root cause: the NINTH FIX's `_reached_bound` only ever anchored hyp to
`ref_norm`'s own START (a free-TRAILING-gap alignment) — a reasonable
assumption for the FIRST rolling window of an āyah, but wrong for every
later one. With `WINDOW_MS=3200` against a 15-second āyah (1:7), most
windows land somewhere in the MIDDLE, not the start. A mid-āyah clip like
"المغضوب عليهم..." was forced through a DP that tried to explain it as
starting from the āyah's own opening ("صراط..."), which it obviously
doesn't — so the computed "reached" boundary came out nowhere near where
the clip's real content was, and the subsequent region-truncated detailed
alignment (also from the NINTH FIX) compared hyp against the wrong slice of
the reference entirely, producing an unpredictable, often-wrong verdict for
words that were actually decoded correctly.

**Fix: `_reached_bound` (single boundary, free-trailing-gap only) replaced
with `_local_reached_region` (a start/end PAIR, free at BOTH ends)** — a
proper local/"fitting" alignment that finds the best-matching contiguous
region of the reference for the fully-consumed hypothesis, handling the
clip being the āyah's BEGINNING, END, or a MIDDLE segment uniformly, with
no assumption about which. `_word_match_ratios` restricted the reached
region to `[reached_start - NOT_REACHED_SLACK, reached_end + 1 +
NOT_REACHED_SLACK]` (padded both sides now, not just one) for the
subsequent detailed alignment, and a word is excluded (`None`) only if its
own span doesn't overlap that padded region AT ALL, from either side —
previously only the "too far ahead" side was checked.

Deliberately safe to do as a genuinely LOCAL (free-both-ends) alignment
here, unlike `content_check.locate_best_span`'s earlier-rejected
Smith-Waterman attempt for finding WHICH āyah a clip belongs to (rejected
for letting a short hyp match almost anywhere across an ENTIRE sūrah by
chance): this alignment only ever searches within a SINGLE, ALREADY-LOCATED
āyah's text (tens of characters), against hyp that typically covers several
whole words (15-30+ normalized characters from a ~3s window) — a
structurally much safer length ratio, and it only decides which words get
GRADED AT ALL, not the final content_ok verdict (still separately
compactness-checked per word via `WORD_GAP_SLACK`, unchanged).

Validated: full suite still 51/53 (no regressions — same pre-existing
pytest-only failure); the SAME real husary mid-āyah clip that exposed the
bug (`.build_tmp/probe_maghdoub.py`, 5.0-8.2s of 1:7) now grades
"ٱلْمَغْضُوبِ" `content_ok=True` (previously always red regardless of how
cleanly it was decoded); re-ran both the isolated-per-āyah regression probe
and the earlier partial-1:7 probe — both unchanged from before this fix,
confirming this only corrects the specific mid-clip case without disturbing
anything already working. Restarted the correction server.

**Known, accepted residual imperfection, not chased further:** a word
sitting at the EDGE of a clip's reached region (e.g. the word immediately
before "المغضوب" in a clip that starts mid-word) can still show red instead
of being excluded in some individual windows — visible in the validation
run above ("عليهم"/"غير" still flagged in isolation). In the REAL rolling-
window session (not an isolated single-clip test), this is substantially
mitigated by the SIXTH FIX's sticky merge: once ANY window correctly grades
a word green, a later window's boundary imprecision can never downgrade it
back to red. Chasing a perfect boundary here would mean re-deriving
something close to true word-level timestamps, out of proportion to the
now-small remaining impact.

User feedback (real-mic testing): "recite correctly, then stay silent — after
a moment it says wrong." Real, correctly-diagnosed-by-the-user bug (not a
grading-model problem): `useAutoRecorder`'s single instance is created once
for the whole ListenRepeat session and never stopped on a pass — only the
STAGE changes (via a delayed setStage()), the mic keeps recording straight
through. The reciter goes quiet after finishing correctly, but the recorder
doesn't; eventually background noise (or the mic's own noise floor) trips
`pauseDetector.ts`'s speech threshold again, cutting a near-silent trailing
segment. That segment gets sent to gradeClip, correctly comes back as not
matching (there's no real recitation in it), and `handleSegment` unconditionally
does `setReport(rep)` before checking pass/fail — so this bogus result
overwrites the correct ✅ with a false "Not quite", and can even bleed into
the NEXT stage if the stage transition has already fired by the time it lands.
Fixed: every pass branch (Echo, Recall, Blind's 2nd clean streak, and the
Blind fallback-to-Recall path) now calls `autoRec.stop()` SYNCHRONOUSLY at
the moment the pass is detected, before scheduling the delayed stage change
— not just relying on the eventual setStage(). Each new stage requires an
explicit "Start reciting" tap, same as entering a stage does today; this is
a deliberate trade (one extra tap per stage) for eliminating the whole bug
class rather than trying to tune the pause detector's threshold, which
wouldn't fix it (the detector is working as designed — the bug was that
nothing ever told it to stop). Still needs the user's real-mic pass to
confirm no more false negatives.

User feedback (real-mic testing, immediately after the fix above): "Not
quite" even when reciting correctly. Second, different real bug, this time
in the pass CRITERION itself. `clean()` in ListenRepeat.tsx (the Recall/Blind
gate) required EVERY word tagged to the āyah to come back `content_ok` —
built fresh for this screen instead of reusing Practice.tsx's already
real-audio-validated PASS_RATIO=0.5 threshold (majority of words content_ok,
clip covers ~all expected words). A handful of individual words routinely
misfire on the ASR even for a genuinely correct recitation — Practice.tsx
already learned this the hard way (see its own PASS_RATIO comment and the
Phase 0 CER-threshold validation notes above) — so a 100%-of-words bar was
guaranteed to false-negative in normal use, not just an edge case. Fixed:
`clean()` now takes the āyah's expected word count and uses the exact same
completeness + PASS_RATIO check as Practice.tsx, still content_ok-based (not
Practice's tajweed-inclusive `verdict`, since Recall/Blind are specifically
checking memorized content, not pronunciation). Lesson for next time: when a
new screen needs a "did they get it right" check and an existing, real-audio
proven one already exists elsewhere in the app, reuse its exact threshold
rather than inventing a fresh, untested one — this is the second bug in this
screen alone from not doing that.

User feedback (real-mic testing, same session): "the second time to recite
[in Blind] is not working." Third bug, same root cause as the very first one
(recorder not stopping on a pass) — just missed in one spot when applying
that fix. Blind needs BLIND_STREAK_TARGET=2 consecutive clean passes; the
`autoRec.stop()` fix was applied when the 2nd clean pass hits target, but NOT
on the 1st clean pass while waiting for the 2nd — the recorder kept
listening through the gap between attempt 1 and attempt 2. Same failure mode
as before: reciter pauses to collect themselves after a correct 1st attempt,
mic stays hot, a trailing-silence segment eventually gets cut and graded,
fails, and the `else` branch's `setBlindStreak(0)` silently resets the
streak back to 0 — before the reciter even gets to attempt the 2nd
recitation. From the outside this reads exactly as "the second recitation
isn't working," since the streak can never survive the gap between attempts
regardless of how well the reciter actually does. Fixed: `autoRec.stop()`
now runs on EVERY blind pass, not just the one reaching target — the 2nd
attempt now requires its own explicit "Start reciting" tap, consistent with
every other stage transition in this screen. Worth noting for future
review of this file: "stop the recorder on every code path that can be
followed by silence" is the actual invariant this screen needs, not
"stop the recorder when transitioning stages" — those aren't quite the same
thing, as this exact miss demonstrates, and it's worth re-scanning
handleSegment once more for any other pass-then-continue-listening path
that might still be exposed to it.

Did that re-scan immediately (same session). Found one more, quieter
instance: on a genuine FAIL (any stage, below FALLBACK_AFTER_FAILS), the
recorder deliberately keeps listening so the reciter can retry without an
extra tap — but that means the exact same trailing-silence risk applies to
the gap between a failed attempt and the retry: a near-silent segment could
get graded, come back as "not passed" again, and increment blindFails purely
from noise (inflating the fail count toward a premature fallback-to-Recall,
or just a confusing extra "Not quite" for something the reciter never said).
Rather than adding autoRec.stop() to every fail branch too (which would cost
an extra tap on every single retry — real UX friction for the common case),
fixed this with a general guard instead: `handleSegment` now discards any
segment whose `decoded_text` is under 3 characters BEFORE touching report,
streak, or fail-count state at all — genuinely not a real attempt, not "a
wrong one." This also acts as defense-in-depth for the pass-side fixes
above, in case the `autoRec.stop()` call ever loses the race against a
faster-than-usual ambient noise blip (cut happens, new segment starts, noise
trips it before grading of the PASSING clip has resolved and called stop()).

User feedback (real-mic testing, same session, screenshot): Recall showed
✅ "Correct." for a genuinely correct recitation — the frontend fixes above
ARE working — but a raw backend error ALSO appeared underneath it: "Échec de
l'analyse audio : ... targets length is too long for CTC. Found log_probs
length: 65, targets length: 120, and number of repeats: 4". Real backend
bug, first one found in this whole Listen & Repeat investigation that isn't
a frontend/recorder issue. Root cause: torchaudio's `forced_align` (called
from `Wav2Vec2Aligner.align_from_decode`, `src/tajweed/correction/
aligner.py`) has a hard CTC constraint — the target token sequence (with
mandatory blanks between consecutive repeated tokens) must fit within the
emission's frame count, or it raises RuntimeError. `evaluate_clip` (`src/
tajweed/correction/evaluate.py`) bounds the candidate text to
`locate_best_span`'s matched [ayah_from, ayah_to] range before force-
aligning, same as always — but the frontend guards added earlier in this
session only close the gap AFTER a segment has already been cut and is
in-flight being graded; they don't retroactively cancel a segment that was
cut and started grading concurrently, before `autoRec.stop()` had a chance
to land (grading is async and takes real wall-clock time, while the
pause-detector's cutting loop runs independently in the background — see the
two frontend fixes just above for the fuller mechanics). So a short/
near-silent stray segment could still occasionally reach the server, get
matched by `locate_best_span` against a candidate span too long for its
actual (short) audio, and crash `forced_align` instead of gracefully
mismatching. `server/app.py` already wraps evaluate_clip in a bare `except
Exception` -> `HTTPException(422, f"Échec de l'analyse audio : {e}")`, so
the raw torchaudio C++ error message was surfacing verbatim to the end user,
confusingly right next to a correct ✅ for the actual real recitation.

Fixed at the source rather than papering over it client-side: `evaluate_clip`
now wraps the `align_from_decode` call in a try/except matching specifically
on "targets length"/"CTC" in the RuntimeError's message (not swallowing
every RuntimeError — a different, genuine bug should still surface loudly),
and on that specific match returns a normal `located=False` /
`content_status="content_mismatch"` ClipReport — the semantically correct
read of this failure: locate_best_span's matched span simply doesn't fit
what's actually in the clip, same as any other bad match, not a hard error.
Added 3 regression tests in tests/test_correction.py (a fake aligner whose
align_from_decode raises the real CTC error message; confirms it now reads
as not-located; a second fake aligner raising an UNRELATED RuntimeError,
confirming that one still propagates and isn't accidentally swallowed by the
same catch). `python -m pytest tests/test_correction.py`: 54 passed, 1
failed — the 1 failure (test_evaluate_clip_locates_and_grades_without_
start_ayah) is pre-existing and unrelated (a locate_best_span tie-break
case, not touched by this change).

IMPORTANT: server/run.ps1 runs uvicorn WITHOUT --reload, so this fix needs
the correction server manually restarted (Ctrl+C, re-run server/run.ps1)
before it takes effect — confirmed still running the old code as of this
fix (health check responded, meaning the process is up but hasn't picked up

    wrong  1:1 audio→1:2 text (adjacent, same surah) cer=0.765  CAUGHT (barely)
    wrong  1:1 audio→112:1 text (both short)         cer=0.433  MISSED
    wrong  112:1 audio→1:1 text (both short, reverse) cer=0.737  MISSED (barely)
  Reading: medium/long ayahs are caught reliably in both directions (comfortable
  margin above 0.75 for wrong, comfortable margin below for correct). SHORT
  ayahs (roughly <15 letters — most of surahs 105-114, opening ayahs) are the
  weak spot, and it's NOT a threshold problem: correct short recitations
  ALREADY sit at 0.63-0.67 CER (just the raw non-Quran-tuned ASR's noise floor
  on so little text), right up against wrong-short-ayah cases at 0.43-0.74.
  There is no threshold value that separates these two clusters — LOWERING it
  to catch the missed wrong-ayah cases WOULD flag correct 112:1/114:1 as
  mismatched (false rejection of a correct reciter). Conclusion: leave
  CONTENT_MISMATCH_CER at 0.75 (safe default, protects the correct-short-ayah
  cases); short-ayah wrong-content detection needs Phase 1's WORD-level
  comparison (a wrong short ayah recited word-by-word should mismatch on
  individual words even when the whole-text ratio is ambiguous) — don't
  attempt to fix this in Phase 0 by threshold tuning alone, it's provably
  not solvable that way with this data.
